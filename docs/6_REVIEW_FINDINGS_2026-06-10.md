### 1.01_pull_observed_prices.py

**Overall:** This unit is sound. It does exactly what the README claims: pulls ENTSO-E day-ahead prices for the 14-country geography (all 22 bidding zones, including the DK1/DK2 and NO/SE sub-zones the validation depends on), converts indices to UTC — which deliberately and correctly matches PyPSA-Eur's naive-UTC 8,760 snapshots used downstream in 1.03/1.04 — handles failed/empty zones gracefully (GB's documented post-Brexit absence in 2023 is confirmed in the output file), and prints non-null counts per zone so gaps are visible. Verified against the actual output CSVs: no duplicate (timestamp, zone) pairs, no DST artifacts, NaN prices confined to GB/IE source gaps. The real issues found are all minor: an end-inclusive query window that writes 8,761 hours per zone (one hour of the next year, harmlessly dropped by downstream dropna alignment), a zone-label schema drift showing the committed 2019 file predates the current script version (\"DE-LU\"/\"IE\" vs \"DELU\"/\"IESEM\" — result-preserving today because downstream keys on country), a stale docstring, and a mkdir that fails on fresh checkouts. Nothing here is result-changing for the calibration, capture-value, or bias-correction chain.

**Runtime:** No meaningful hotspot. Runtime is dominated by ~22 sequential ENTSO-E API calls plus a 0.4 s sleep per zone (~10 s of sleep total); the per-row Python loop building ~184k dicts (lines 77-83) is sub-second territory. This script is irrelevant to the author's overall runtime complaint — the cost lives in the Gurobi solves of 1.07/1.10/1.13, not here. If desired, the row loop could be replaced with per-zone DataFrames + one concat, but the gain is negligible.

  - Where: lines 55-56, 68 (query window / query_day_ahead_prices)

### 1.02_run_baseline.sh

**Overall:** The shell wrapper's mechanics are sound: correct snakemake invocation, sane logging, caffeinate against sleep, and caching honestly delegated to Snakemake (no wasteful re-solving). But auditing what it actually launches uncovered a critical, result-changing method deviation. The configs it feeds to snakemake were written for an older PyPSA-Eur: they set the now-removed `scenario: ll: [\"v1.0\"]` wildcard, which v2026.02.0 silently ignores, so every network was prepared with the default `transmission_limit: vopt` — all AC lines and DC links extendable with no volume cap. The solved networks prove it: 0 global constraints everywhere; +2.5 GW line expansion in the 2019 baseline, +24 GW lines / +5.7 GW links in the 2023 calibration baseline, and +133.6 GW lines / +14.7 GW links in the canonical v3 2040 Baltic-high scenario. This contradicts the documented 'transmission frozen at today's level' on which the calibration, the DK2 bias narrative, the 1.09 bias correction, and the cannibalisation headline all rest, and it propagates downstream because 1.07 freezes generators but not branches. One minor reproducibility gap: the script is hardcoded to 2019 with no committed path to reproduce the 2023 run. Fix the config key, re-run, and the rest of the wrapper can stand as-is.

**Runtime:** The wrapper itself is not a hotspot (it backgrounds snakemake under caffeinate and relies on Snakemake's incremental caching, which is the right design — re-runs skip up-to-date steps). However, the vopt defect is also a major runtime tax: with all 48 lines and 50 links carrying extendable capacity variables, every solve becomes a planning LP in which 98 capacity variables couple all 8,760 snapshots, instead of the near-decomposable pure-dispatch LP the method intends. Fixing `transmission_limit: v1.0` (non-extendable branches) should noticeably speed up the baseline solves, the 6 canonical scenarios (~50 min), every gas-shock grid cell (5-20 min each), and the 50 surrogate runs — the correctness fix and the speedup are the same change. Note that because Snakemake 9.20 includes params in its default rerun triggers, the config fix will automatically invalidate prepare_network/solve_network without needing --forcerun.

- **[CRITICAL | method-deviation]** Documented frozen transmission (ll=v1.0) is silently ignored — all runs solved with unconstrained optimal transmission expansion (vopt)
  - Where: scenario block, line 30 (`ll: ["v1.0"]`); same defect in config.faisal-2023.yaml; symptom visible in 1.02_run_baseline.sh line 16 (TARGET=results/faisal-2019/networks/base_s_30_elec_.nc — no lv1.0 segment)
  - Evidence: The config sets `scenario: ll: ["v1.0"]  # line volume limit: keep transmission at today's level`, but the installed PyPSA-Eur is v2026.02.0 (git describe: v2026.02.0-39-g23c2fac7), where the {ll} wildcard no longer exists: grep for `{ll}`/`wildcards.ll` across ~/pypsa-eur/rules/*.smk and Snakefile returns nothing, and the solved-network pattern is `base_s_{clusters}_elec_{opts}.nc` (rules/solve_electricity.smk:10). Transmission limits are now read from `electricity: transmission_limit` (rules/build_electricity.smk:874: `transmission_limit=config_provider("electricity", "transmission_limit")`), which neither faisal config sets (grep exit 1), so the default `transmission_limit: vopt` (config.default.yaml:185) applies. In scripts/prepare_network.py:159-197, factor=="opt" makes every AC line and DC link extendable (`n.lines["s_nom_extendable"] = True`; `n.links.loc[links_dc_b, "p_nom_extendable"] = True`) and, because `factor != "opt"` is False, NO lv_limit GlobalConstraint is added. With ll=v1.0 as documented, set_transmission_limit would have kept lines non-extendable (factor 1.0 fails the `> 1.0` test) and added an `lv_limit` constraint. So the 2023 price calibration (median |bias| ~7%) was achieved on a grid with 24 GW of phantom reinforcement, and the canonical 2040 Baltic projection allowed 133.6 GW of free cost-optimal grid buildout — directly contradicting README/config claims and biasing exactly the quantity the thesis studies: congestion-driven price depression in small zones. It also plausibly contributes to the documented DK2 'shadow prices too flat in windy hours' bias that 1.09's correction is built on, partially making the bias-correction a patch for a config bug. 1.07_run_scenarios.py freezes generators (`n.generators.loc[ids, "p_nom_extendable"] = False`, lines 175/231) but never resets lines/links, so the defect propagates to every projection, gas-shock, and surrogate run.
  - Fix: In both configs add `electricity: transmission_limit: v1.0` and delete the dead `scenario: ll:` and `scenario: simpl:` keys (the {simpl} wildcard is also removed in this PyPSA-Eur version). The target filename is unchanged (`base_s_30_elec_.nc`), and Snakemake 9.20's default rerun triggers include params, so re-invoking 1.02 will automatically re-run prepare_network and solve_network. Then re-run the downstream chain (1.03-1.05 validation, 1.07-1.11 projections/gas-shock, 1.12-1.15 surrogate) and re-fit the 1.09 bias regression on the corrected networks. As a belt-and-braces guard, have 1.07 assert `not n.lines.s_nom_extendable.any()` after loading the baseline.

  - Where: lines 2, 7-9, 15-17 (header comment, usage examples, CONFIG/TARGET/LOG)

### 1.04_observed_capture_values.py

**Overall:** The computational core is sound: the CV formula (generation-weighted price over time-mean price on aligned hours) is correctly implemented, timestamps are handled consistently in UTC (verified 8,760 naive-UTC snapshots vs tz-aware observed data), the DK1/DK2 longitude split at 11.0E is verified correct against actual bus coordinates (DK1 0 at 9.78E, DK2 0 at 12.28E) and is identical to 1.07's convention, and the output CSV reproduces the README's quoted numbers exactly (DE 2023: 0.910 vs 0.909; DK2: 0.945 vs 0.784). Headline 2023 DE/DK2 results survive all four findings.

**Runtime:** No hotspots in this unit. Wall time is dominated by the single ~33 MB pypsa.Network() load (tens of seconds). The author's runtime complaints originate in the solve-heavy scripts (1.07/1.10), not here.

### 1.05_analyse_baseline.py

**Overall:** The script's structure is sound — verified against the actual solved network: snapshot weightings are all 1.0 hourly (so the capacity-factor formula energy/(p_nom*8760) is correct), every renewable generator has both a price-bearing bus and a dispatch time series (no silent drops), load shedding is negligible (0.16 MWh total, so VOLL does not contaminate mean prices), the hardcoded carrier list covers all renewables present (no offwind-float in this network), and the capture-price numerator (generation-weighted bus shadow price) is implemented correctly and matches 1.04's numerator. However, two real problems exist in the denominator chain. First, a genuine math bug: the 'load-weighted' country price is an unweighted mean of per-bus weighted prices, which inflates NO's price by 2.7 €/MWh and deflates its published offshore CV from ~0.98 to 0.913 — the figure's apparent NO cannibalisation is an artifact. Second, a method inconsistency: 1.05 divides by this load-weighted price while the validation script 1.04 (basis of the bias correction) divides by a simple time-average, and the file's own docstring claims a third definition (bus-level time-average); the definitional spread is 0.04-0.07 in CV. Mitigating: no downstream script consumes baseline_2019 outputs, so the projection/bias-correction chain is untouched — the damage is confined to baseline thesis tables and figures.

**Runtime:** This unit is not a runtime hotspot: it loads one 52 MB netCDF (a few seconds) and all per-country/per-generator Python loops operate over at most 30 loads and a few hundred generators with vectorized inner operations.
